# Audience (CRM)

## Projection

- The CRM is a read-side projection: never change order, attendee, check-in or waitlist behaviour for it. Everything derived from them (activities, contact rollups, `crm_contact_spend`, order opt-ins) must be rebuildable by `CrmProjectionRepository::projectOrders`/`projectWaitlistEntries`; only tags, notes, merges, non-order consent, segments, campaigns and imports are CRM-owned.
- Projection deletes and re-inserts per order: keep it idempotent and set-based. Resolve every email through `crm_contact_emails` (that is how merges hold) and never create a contact whose hash is in `crm_deleted_contacts`. Tombstone hashes use the organizer's salt in `crm_deleted_contact_salts` (never `APP_KEY`, never a `crm_organizer_states` row) via `DeletedContactHasher`; recreating a deleted contact by hand needs `restore_deleted` and re-projects that email's history. A tombstone also records `sms_opted_out`; every restore (by hand or a confirmed signup) re-projects the history inside the restoring transaction and then opts the current number out again. A suppression is never lost to a delete: every tombstone of a contact carries an opt-out or complaint made on any of its addresses (a bounce stays with the address that bounced). A tombstone holds one `suppression`, ranked complained > unsubscribed > bounced (`CrmEmailMarketingStatus::suppressionStrength`) wherever it is chosen or upgraded (delete, late events, suppression import): staff can clear a bounce but never an opt-out, so the opt-out wins and restores as `UNSUBSCRIBED`. An unsubscribe link, bounce or complaint feedback or text opt-out link that arrives after the delete strengthens the tombstone through the recipient's `deleted:<hash>` placeholder (`strengthenDeletedRecipientSuppression`, `markDeletedRecipientOptedOutOfTexts`). The unsubscribe and text opt-out pages of a deleted contact read that tombstone (`findDeletedRecipientTombstone`), never assume: they offer the button until it holds an opt-out or complaint (or `sms_opted_out`; a bounced tombstone still offers it and the opt-out replaces the bounce), return no `email` or `phone` (the page words itself without one) and never offer to resubscribe. A restore re-links those recipient rows to the new contact (`relinkDeletedRecipients`), so old links, late feedback and the 30-day wait after a provider refusal keep applying. A STOP reply from a deleted contact's number is not matched to a tombstone, by design (no phone hash is kept; Twilio blocks that number itself).
- Normalize emails with `ContactEmailNormalizer` in PHP and `lower(btrim(x, ContactEmailNormalizer::SQL_TRIMMED_CHARACTERS))` in SQL.
- Every write that touches contacts or consent takes the organizer advisory lock first and resolves the contact inside it (`LocksCrmOrganizer`), so it can't race `projectOrders`.
- Sources without a domain event (waitlist joins, abandoned checkouts, self-service attendee edits, deletions) are caught up by `ReconcileContactsJob` → one `ReconcileOrganizerContactsJob` per organizer, keyset-paged; a gap over `MAX_CATCH_UP_HOURS` runs a full sync and `reconciled_until` only moves once it finishes. A full sync visits live orders and entries, then re-projects whatever is still projected from ones that are no longer live (`findProjectedOrderIdsNoLongerLive`, `findProjectedWaitlistEntryIdsNoLongerLive`), so deletions during the gap are removed too. A new source table needs a projection, a changed-since query and an `(event_id, timestamp)` index.
- `ContactSyncListener` runs inside order completion: one indexed lookup in a savepoint, dispatch a job keyed on the order, never throw. Syncing only happens for organizers with a `crm_organizer_states` row on an account with the `crm` flag; projection jobs re-check that, and tests projecting a second organizer call `trackOrganizer`.
- No-shows are computed, never stored, only for ended occurrences with at least one check-in. Guest tickets never count as the buyer attending.
- Deleting a contact removes CRM rows only (and their pending signups, which hold consent proof).

## Consent

- Only `SUBSCRIBED` contacts are mailable. Status comes from the ledger across all of a contact's emails: `COMPLAINED` if any email complained, `BOUNCED` if the primary hard-bounced, else the latest primary opt-in vs any opt-out, else `NOT_SUBSCRIBED`. Every status query goes through `ConsentStatusSql` (built on `ConsentSupersedeSql`).
- Ways in: completed-order opt-ins (an order's opt-in is cleared when its email is changed to another address, by staff or the buyer, so it never follows the order to someone who did not give it), attested imports, a confirmed signup form (`FORM`, the only verified opt-in: it supersedes an earlier bounce or complaint on that email) and the contact undoing their own unsubscribe link (`CONTACT`). Staff can only opt people out. `BOUNCE_CLEARED` (staff reactivating a bounce, never a complaint) makes a bounce stop counting; it is refused for 30 days after a provider refusal (`BounceReactivationPolicy`, exposed as `reactivation_available_at`) and never opts anyone in.
- Merge and split move consent events with their emails. The source unique index on both ledgers includes `email`, so two addresses with the same source (one import, one opt-out link) each keep their own event; a merge only drops a row that repeats the same source for the same address.
- The suppression list is a view: the contacts list's Suppressed scope (`?segment=suppressed`) lists `UNSUBSCRIBED`/`BOUNCED`/`COMPLAINED` contacts through the normal endpoint with `with_suppression=1`. Tombstones are counted and looked up, never listed. A suppression import only writes `OPT_OUT`/`BOUNCED`/`COMPLAINED` (source `IMPORT`), creates unknown addresses as contacts, never weakens a suppression and upgrades a tombstone's `suppression` (same ranking) without recreating the contact. For a live contact the ledger keeps each reason: the imported one is recorded unless the address already complained or already holds that reason, so an imported unsubscribe outlasts a bounce staff later clear. A bounce listed only for a secondary address is recorded but does not suppress the contact, so it is reported as `bounced_secondary_address`, not as suppressed (preview and result).

## Campaigns

- Every send goes through `CampaignLaunchService`: `CampaignSendGate`, then review in SaaS mode (untrusted accounts, each account's first campaign, audiences with import-only opt-ins no approved campaign has reached). The row is re-read `FOR UPDATE`; gate, status change, `launched_at` and the recipient snapshot run in one transaction under a per-account lock; jobs dispatch after commit. Never dispatch `DispatchCampaignJob` another way. The daily cap counts manual campaigns only.
- Status groups live on `CrmCampaignStatus` (`editable()`, `resolvingAudienceLater()`, `withdrawable()`, …); never write status lists by hand. `transitionStatus` is for status changes only; edits use `updateIfEditable`.
- Scheduled campaigns are read-only ("Move back to draft" cancels; for an automation's run the same action is worded "Cancel this email" and confirmed, because the run ends `CANCELLED` and its recipients are never retargeted). A rejection clears `scheduled_at`. A schedule needing review is reviewed at schedule time (`PENDING_REVIEW` with `scheduled_at`, recipients snapshotted); approval makes a future one `SCHEDULED` with `approved_at` and `launchScheduled` releases it without re-running the gate. A failed scheduled send returns to draft and emails the creator. A scheduled campaign still unsent `CampaignLaunchService::SCHEDULED_SEND_WINDOW_HOURS` after its time (licence or flag off, worker down, or still in review: approving it then is a 409) returns to draft with a reason and `CampaignNotSentMail`; it is never sent late. `SendScheduledCampaignsJob` is therefore scheduled without the licence check (`CrmSchedulerTest`); it only launches with a licence. Releasing an approved scheduled text re-checks `CRM_SMS`.
- `status_reason` holds a code only (params derived in the resource), never a sentence; the frontend words it and the owner's email is written in the owner's locale (`CampaignOwnerNotifier::inOwnerLocale`).
- A blocked send (`meta.send_gate`, `send-check`) returns the sentence plus `blocked_reason_code` and `blocked_reason_params`. Every place that shows it renders `SendGateReason`, which turns `ACCOUNT_NOT_APPROVED` into a link to payout settings for members with `MANAGE_PAYMENTS`: finishing Stripe Connect sets `is_manually_verified`, so the copy must never say accounts are only enabled by hand.
- An approval carries the `updated_at` the reviewer saw (`reviewed_version`), so anything that changes a `PENDING_REVIEW` campaign must bump `updated_at`.
- With `CampaignAiReviewService::isEnabled()` (SaaS mode, `APP_CRM_CAMPAIGN_AI_REVIEW_ENABLED`, an Anthropic key) a campaign entering `PENDING_REVIEW` goes to `ReviewCampaignWithAiJob` instead of the support inbox. `CampaignAutoReviewService` stores the verdict in `ai_review` (cleared on every submit) and approves through `CampaignLaunchService::approve` with the version it read; anything else (not approved, under the confidence threshold, can't be sent, job failed) is recorded as `NEEDS_PERSON` and only then emailed to support. The check never rejects. The prompt is built from what recipients will see (`CampaignReviewAgent`); campaign text is untrusted, so angle brackets are replaced before it enters the prompt. A campaign the check can't read in full goes to a person without asking the model: a body with an image, or more text or links than the prompt carries (`UntrustedPromptText::holdsMoreThanIsRead`).
- Cancel/reject withdraws recipients in the same transaction: manual rows are deleted, automation rows kept as `SKIPPED` (and the campaign ends `CANCELLED`) so later runs don't retarget them; automation campaigns can't be deleted. Stopping `SENDING` skips `PENDING` rows. The health guard's `PAUSED` is final, and delivery skips a `PENDING` row of a `PAUSED` or `CANCELLED` campaign (`CAMPAIGN_STOPPED`). A `PENDING` recipient only counts as reached while its campaign is `SENDING` or `PENDING_REVIEW`.
- A suspended account sends nothing: `CampaignDispatchService::pauseIfAccountSuspended` (dispatch and every delivery, email and text) pauses a `SENDING` campaign for good with `ACCOUNT_SUSPENDED` and skips its pending recipients, `launchScheduled` leaves a due campaign alone (it returns to draft after the send window, as with the flag off) and `RunAutomationsJob` skips the account's automations.
- A campaign with recipients is never deleted. A recipient is claimed (`PENDING`→`SENDING`) after its mail is built and before it goes out; `CampaignTransportErrorClassifier` decides what a transport error means from the HTTP status or SMTP reply code and how far the exchange got, never from the error text, for every mail provider. Only an error the provider can't have accepted puts the recipient back (connection never opened, SMTP failure before `DATA`, an SMTP 4xx reply, HTTP 408/429/503), and the job retries those for `SendCampaignEmailJob::RETRY_WINDOW_MINUTES` before failing the recipient with `PROVIDER_UNAVAILABLE`. A refusal (SMTP 5xx, other HTTP 4xx) ends `FAILED` `PROVIDER_REJECTED` at once; anything else after the message left (other 5xx, reset, timeout) ends `FAILED` `TIMEOUT` and is never retried. Every skip or failure stores a `CrmRecipientFailureReason`. Report stats count `undelivered` (carrier receipts, `UNDELIVERED`) apart from the other failures; the report's "skipped or failed" excludes them. A provider saying the address is bad (Postmark "inactive recipient", an SMTP 5.1.x/5.2.1 reply to `RCPT TO`) is `PROVIDER_SUPPRESSED` plus a `BOUNCED` consent event, counted by the health guard. Bounce and complaint feedback, and so the health guard, need a delivery webhook receiver (Postmark today); the resource says so with `delivery_reports_available`.
- Records a campaign links to (event, promo code, automation, segment) can be deleted after launch: use `findFirstWhere` and handle null.
- Content: placeholders come only from `CampaignTokenCatalog` (event tokens only with a linked event or an event trigger; templates take none), the only filter is `| default: "…"`, unknown ones are a 422 on save and block a send. HTML is stored and rendered through `CampaignHtmlSanitizer` (no CSS background or list-style images, `<img>` only from our CDN/storage with no dot segments in the path), never the bare purifier. Bodies reach the Markdown layout as one line inside a `<div>` so Markdown is never parsed.
- Early access (`early_access_product_ids`): when sending starts (after approval), `EarlyAccessService` hides those tickets and creates a one-off promo code for exactly them; drafts never touch the event. The campaign records the tickets it holds hidden in `early_access_hidden_product_ids` (the ones it hid, plus ones already held by another campaign; tickets the organizer hid beforehand are never held). Ending early access un-hides only those, skips any another campaign still holds, and empties the list; the resource's `early_access_releasable_product_ids` is what ending would make public. A null list (launched before it was recorded) falls back to `early_access_product_ids`. The event must be `LIVE` with those tickets: `findOfferableTickets` blocks the send check and the submit (before review or scheduling) and guards the release again.
- Delivery caches a campaign's event context for 60s per locale; previews never do. Mail is built inside `withLocale`; automation `{{ event_date }}` is rendered per recipient there. A campaign with only `event_occurrence_id` (the after-event thank-you) still takes event placeholders, resolved through the date's event, but gets no event card. The footer shows the organizer's postal address (its `location_record` structured address) when it has one; sends are never blocked without it. Campaign mail goes out under the platform From name with the organizer as Reply-To, and only in SaaS mode (`app.saas_mode_enabled`) opens with the "from :organizer, not from :platform" line (HTML and text), which accounts that paid to remove Hi.Events branding never get (`MailBrandingDTO::hideHiEventsBranding`); previews return both (`CampaignSenderName`) so the UI never guesses. `GET campaigns/{id}/preview` is the read-only preview for both channels (email HTML, or a text's rendered variants) and needs no licence, so viewers and lapsed accounts never see raw placeholders.
- Templates are organizer-scoped content (no audience or event), unique names case-insensitively, at most 100. Starters are code-defined (`CampaignStarterTemplates`). Duplicating never copies status, recipients, schedule, promo code, automation link or review note.

## Automations

- `AutomationRunner` only creates a normal campaign and hands it to `CampaignLaunchService`; each trigger is a class in `Automation/Trigger/`. Runs are keyed (`automation_run_key`) so each fires once. Switching one on never emails about the past (baselines, `enabled_at`; the announcement baseline is every event that is not a draft, so one that was unpublished or held for review at the time is not announced when it returns); `SegmentEnteredTrigger::baseline()` is the only place that baselines.
- A run that fails for a reason that may pass deletes its draft (freeing the key) and stores why in `last_failure_reason` as a code plus params (`AutomationFailureDTO`, taken from `CampaignNotSendableException::$reasonCode`), never a translated sentence; the resource exposes `last_failure_reason` + `last_failure_reason_params` and the frontend words it. Only "nobody opted in" consumes the key (announcements, follow-ups and both kinds of reminder keep a `CANCELLED` `AUTOMATION_SKIPPED` marker). A run with nobody to email clears `last_failure_reason` unless only a sent email can prove it fixed (`REVIEW_EXPIRED`, `TOO_MANY_RECIPIENTS`, `LINKS_NOT_ALLOWED`), and a refusal is never cleared by another run of the same cycle. A draft holding a key for 10 minutes is a crashed run: discovery ignores it and each run deletes that automation's orphaned drafts first.
- Segment-entry memberships are recorded once the run settles (never for a run whose key another run of the same slot already holds: those entrants wait for the next slot) and never removed when a contact leaves, so each contact is emailed at most once per baseline (re-baselined when the definition hash changes); merge and split carry them.
- An automation is never reviewed itself: each run is a campaign that goes through `CampaignLaunchService`'s gate and review, so edits to a switched-on automation take effect on the next run. A run still in review `AUTOMATION_REVIEW_WINDOW_HOURS` after launch is cancelled (`REVIEW_EXPIRED`, recipients kept `SKIPPED`) and the automation's `last_failure_reason` says so until a later run is actually sent. A reminder in review whose date has started, was cancelled or is no longer on sale is cancelled the same way when someone tries to approve it. Switching an automation off or deleting it cancels its runs in review and stops the one being sent (`AUTOMATION_STOPPED`, `CampaignLaunchService::cancelRunsOfStoppedAutomation`); approving a run whose automation is off or gone withdraws it instead. While an abandoned-checkout or segment-entry automation has a run in review, later runs are held and sent as one. Reach is 0 with "from now on" copy for welcome, segment entry and abandoned checkout. The preview of a saved automation sends its `automation_id`, so reach leaves out people inside the repeat window and a daily automation that already ran today reports tomorrow's run. Reminders default to ticket holders.
- Abandoned checkout reads `orders` read-only (never box office, payment-link, manual or waitlist-offer orders), only reaches already-`SUBSCRIBED` contacts and sets `skips_buyers`.
- Send times: reminders go at 10:00 in the event's timezone, welcome and win-back once a day from 10:00 in the organizer's timezone (run key `date:<organizer-local date>`).
- Each run is bounded and the next 15-minute run continues: `MAX_EVENTS_PER_RUN` announcements, follow-ups and reminders (the reminder's is-due rules are in SQL so the limit only counts due dates), `SegmentEnteredTrigger::MAX_ENTRANTS_PER_RUN` entrants. Segment-entry and abandoned-checkout runs never name more contacts than the account's tier may email at once (`CampaignSendGate::maxRecipientsPerSend`), so a large batch drains over several runs instead of being refused forever.
- The announcement only waits for a spam check when `EventSpamCheckService::isEnabled()`. An event still without a passing check `EventPublishedTrigger::SPAM_CHECK_WAIT_MINUTES` after its last edit is reported as `EVENT_AWAITING_REVIEW` (and its check is queued again when it has none); it is announced if it passes later, never unchecked.

## Text messages (SMS)

- Bring-your-own Twilio per organizer (`crm_sms_connections`, auth token encrypted, never in a resource). Everything goes through `SmsProviderInterface`; `SMS_DRIVER=fake` swaps in `FakeSmsProvider` for e2e and phpunit only, so it is deliberately absent from the `.env.example` files. The `CRM_SMS` flag gates connecting and launching; disconnecting works without a licence. A Messaging Service belongs to one organizer (inbound STOP replies go to a single webhook), so `SmsConnectionService::save` refuses one another organizer has connected. Every save replaces that service's incoming-message webhook at Twilio (`configureInbound`) and disconnecting never restores it; the connect form and the disconnect dialog say so. `FakeSmsProvider` derives its service from the account SID, so e2e gives each organizer its own (`fakeTwilioAccount()`). It keeps every text it sent for an hour in the cache per account SID and number (`sentTo`, which throws unless the driver is fake); e2e reads delivered bodies with `sentTexts()` and sends a text held for sending hours with `deliverWaitingText()` (real delivery, clock moved to the country's next sending time). Its three test numbers (`NUMBER_THAT_GETS_THE_ACCOUNT_REFUSED`, `NUMBER_TWILIO_REJECTS`, `NUMBER_OPTED_OUT_AT_TWILIO`, mirrored in `e2e/utils/twilio.ts`) fail a send the way Twilio would. The checkout text opt-in settings are shown only where `useTextMessagesVisible()` is true. Checkout offers the opt-in only through `CheckoutSmsOptInService::isOffered` (event setting on, mobile asked for, `CRM` and `CRM_SMS` enabled for the account, the event's organizer has a Twilio connection; the checkout settings warn when it hasn't) and records it only through `isRecordedFor`, which also needs the number's region to be an `SmsCountry` (GG/JE/IM and US territories are their own regions, so not GB/US): an opt-in sent for any other number is silently not recorded, never a validation error, and the checkout page shows the box only once such a number is entered (`isInTextMessageCountry`), unticking it when the number stops qualifying. The stored setting is kept while the flag is off, so it comes back when the flag does.
- SMS consent is its own ledger (`crm_sms_consent_events`) and status (`sms_marketing_status`), separate from email. Ways in: the checkout opt-in box (only shown when the event asks for a mobile number and the buyer's is in an `SmsCountry`) and a START reply from someone currently unsubscribed. Staff can only opt people out. Every opt-out (link in a text, staff, STOP reply, provider opt-out rejection) is for the number: `ConsentRecorder::recordSmsOptOutForNumber` (replies, staff) and `recordSmsOptOutForRecipient` (link, provider rejection; also marks the tombstone when the contact is gone) write it for every contact of the organizer holding that number; only a tombstone restore opts out one contact. The status reads the number's opt-outs across the organizer (`refreshSmsMarketingStatus`), so a contact who takes back a number someone else opted out meanwhile is `UNSUBSCRIBED` until they opt in again. A link opt-out is upserted on its recipient, so an old link works again after a new opt-in. A contact's number comes from its newest completed or awaiting-payment order only, so refunds, cancellations and abandoned checkouts never change it.
- An SMS campaign is a normal campaign with `channel = SMS`: same `CampaignLaunchService`, gate and review. Recipients are `SUBSCRIBED` contacts with a number in a country the connection enables (`SmsCountry`); a number shared by several contacts is snapshotted and counted once (most recently active contact). Consent, number and country are re-checked at delivery and texts only go out in that country's sending hours; while waiting the dispatcher wakes at most every 10 minutes and the resource lists the held countries (`sms_waiting`). Automations are email-only, and the `sms_subscribers` preset can only be saved on a text campaign (422 on `preset` for an email campaign or an automation).
- `CampaignSmsComposer` adds the organizer name and the opt-out line (reply STOP, or a link where replies don't work). Previews and test texts never carry a signed opt-out link (`CampaignUnsubscribeTokenService::sampleSmsUrl()`); lengths and parts are measured server-side (`SmsLengthCalculator`). Early access needs `{{ event_url }}` in the body or the send is refused.
- A recipient is claimed before the provider call. `TwilioSmsProvider` classifies failures from the HTTP status and whether any request bytes left, never from the error text: only 429/503 and "nothing was sent" go back to `PENDING` (retried for 2 hours, then `PROVIDER_UNAVAILABLE`); other 5xx and errors after the request left may have been accepted, so they end `FAILED` `TIMEOUT` and are never retried; other 4xx end `FAILED` `PROVIDER_REJECTED`. A provider opt-out rejection is `PROVIDER_SUPPRESSED` plus an `OPT_OUT` consent event. A refusal of the account or sender (`SmsProviderException::$connectionRefused`: 401, or Twilio codes 20003/20005/20403/21701) or a connection removed mid-send is not a recipient failure: the campaign is `PAUSED` (`SMS_CONNECTION_REFUSED` / `SMS_DISCONNECTED`), the rest are skipped `CAMPAIGN_STOPPED` and `CampaignOwnerNotifier::notifyStoppedSending` emails the creator. A carrier `undelivered`/`failed` receipt ends `FAILED` `UNDELIVERED`. Deleting a contact nulls `phone` on their recipient rows; `phone_country` stays and is what marks a recipient row as a text.
- Twilio webhooks (replies, delivery status) are public routes authenticated only by the request signature, checked against that connection's token and the exact URL for that webhook kind. Replies are scoped to the connection's organizer and prefer Twilio's `OptOutType` over the keyword list. A connection's `public_id` is derived from the organizer, so reconnecting keeps the webhook address; disconnecting changes nothing at Twilio and replies are refused until reconnected. `FakeSmsProvider` verifies real Twilio signatures. Their throttle (`crm-sms-webhook`) is keyed on the webhook kind and the connection's public id, never the caller's IP: Twilio calls for every organizer from the same addresses. Receipts and replies have separate allowances, sized from the dispatcher's fastest send rate (`TwilioSmsWebhookPublicAction::maxRequestsPerMinute`), so receipts can't starve STOP replies.

## Segments, contacts, bulk

- Segment rules reach SQL only through `SegmentDefinitionNormalizer` then `SegmentQueryCompiler`. Spend rules need `VIEW_FINANCIALS`, including through a reused segment; resources strip them otherwise (`has_restricted_rules`).
- Segment counts are cached per definition; the segment list never counts, `segments/count` counts one segment or preset (plus the numbers textable in the connection's countries). The `sms_subscribers` preset is only listed with `CRM_SMS`. The Overview's repeat figure is the `repeat_buyers` preset's count (at least one order and two events), never a second definition.
- The venue rule (`ticket_location`) matches the venue of the date the ticket is for: `coalesce(event_occurrences.event_location_id, events.event_location_id)`, the same fallback ticket emails use.
- The contacts list has one scope picker (all, ready-made segments, your segments, Suppressed) plus a filter that applies exactly its complete rules and replaces the scope. It opens with the selected segment's rules, and empty on All contacts or on a segment whose spend rules the member can't see (that segment shows a notice instead of a list). A filter the API rejects (422) is never retried: the rule errors show in the panel with "Clear filter". "Save as segment" is the only way to keep a filter; column choice is per-browser.
- Bulk actions snapshot the selection into `crm_bulk_operation_contacts` in the same transaction; `BulkOperationProcessor` applies 500 contacts at a time under the organizer lock (inline up to 500, otherwise each `ProcessBulkOperationChunkJob` queues the next, so one chunk per operation is ever queued); no progress for 30 minutes marks it failed (on poll, before a destructive action, and daily by `PruneCrmBulkOperationsJob`, which also deletes snapshots a week after their operation finished, `SNAPSHOT_ROWS_PER_RUN` at a time). Unsubscribe and delete need `confirmation_count` equal to the snapshot (409 `SELECTION_CHANGED`) and only one runs per organizer, checked under the organizer lock. A tag operation carries exactly one tag, so undo (same user, tag operations only, 10 minutes from when the operation finished) reverses exactly what it changed, 500 contacts per transaction. A tag used in segment or unsent campaign rules can't be deleted (409). Bulk unsubscribe records the opt-out for every selected contact whose latest choice is not already an opt-out: never-subscribed ones too (the confirmation says so) and bounced ones, so clearing the bounce leaves them unsubscribed.
- An import stores its parsed rows in `crm_import_rows` and `ContactImportRunner` applies 500 at a time, each chunk in its own transaction under the organizer lock (inline up to 500 rows, otherwise each `ProcessContactImportChunkJob` queues the next). Rows are deleted as they are applied, a failed import keeps the chunks already applied, and no progress for 30 minutes marks it failed. An imported address must pass the same check as the Add contact form (`email`, 254 characters); one listed more than once keeps its strongest suppression reason (complained > unsubscribed > bounced, `CrmEmailMarketingStatus::suppressionStrength`; an import row carries one reason).
- Pick tags with `CrmTagSelect`; the bulk bar keeps its `TagPicker`. An unknown id in a list field (`tag_ids`) is a 422 on that field; a single referenced record outside the organizer is a 404.

## Signup forms

- Always double opt-in: a submission only creates a `crm_pending_subscriptions` row (sha256 token, `SubmitSignupFormHandler::CONFIRMATION_DAYS`) and sends the fixed-copy `SubscriptionConfirmationMail` (the organizer name goes in on one line, like every CRM mailable, so it can't open a Markdown block). `SignupSubmissionLimiter` caps confirmation mails to an address per organizer per day, the number of different organizers that may mail an address in a day (it counts organizers, not mails, so repeat submissions to one form never lock the address out of another organizer's) and mails per form per hour. The submission throttle (`crm-form-submit`) is keyed on IP and form, so a venue's shared wifi has its own allowance per form. `crm_pending_subscriptions.ip_address` and `user_agent` are write-only consent proof, kept deliberately. The response is identical whatever happens, limits included; only a failed Turnstile check (fails closed here) is a 422. `GET /public/crm/confirm/{token}` never confirms (it reports the link lifetime as `link_lifetime_days`); the `POST` does, under the organizer lock. An earlier, unexpired link still confirms and retires the newer one.
- Public pages: `/subscribe/:publicId`, `/widget/forms/:publicId` (`data-hievents-form`), the organizer page band and `/audience/confirm/:token`. New public CRM pages go in `authErrorRedirect.ts`'s allow-list. Public form routes never check the licence; they hide forms of accounts without the `crm` flag.
- The token pages (`/audience/confirm/:token`, `/audience/unsubscribe/:token`, `/u/:token`) share `SubscribePage/StatusPage` (one `h1`, which is also the tab title, `noindex`) and are server-rendered by `tokenPageRouteLoaders`, which only ever `GET` the status; a token the route pattern rejects (404) reads as "This link isn't valid". Public pages never show a raw API `message`: signup errors are worded by `signupSubmissionError` (server text only for a 422).
- A form is public only while its account's email is verified and its organizer is `LIVE` (`SignupFormPublicationGate`, applied by `SignupFormPublicLookup`): otherwise the form, its submissions and the organizer page band answer exactly like a missing form. Making a form `ACTIVE` in that state is a 409 (the Forms page says why and saves new forms paused); an already-`ACTIVE` form keeps its status, can still be edited and comes back when the organizer is published again. Links already emailed still confirm.

## Access, jobs, cache

- The audience stays visible read-only after the licence lapses whenever the account has contacts, an enabled automation, an active form or a recent campaign (`isAudienceInUse`, which feeds `features_in_use`).
- An audience that has synced once (`synced_at`) is built for good (`isAudienceBuilt`): a failed refresh shows a notice with retry above the page, never the first-run screen. The contact drawer offers "Unsubscribe from emails" for the same contacts bulk unsubscribe changes (subscribed, never subscribed, bounced without an opt-out).
- Reads, deletes, cancelling and unsubscribing work without a licence (`authorizeCrm`); creating, editing, importing and sending use `authorizeCrmChange` and `ee.licensed:crm`. All CRM routes are session-only. CRM access needs organizer-level access; the event dashboard's Audience section (`EventDashboardAudience`, no per-event Audience page) shows only to members who can manage the organizer. In the frontend gate writes with `useCrmAccess()` (`canChange`, `canRemove`).
- CRM jobs share the `default` queue with order mail: keep `$timeout` well under `retry_after` (60s), never loop over all organizers, automations, due campaigns or recipients in one job (fan out from a bounded query), and queue campaign mail in waves.
- Counts and insights are cached under `CrmCacheVersion`; every write that changes contacts, consent, tags or activities bumps it after commit. A campaign's delivery stats are cached per campaign and status (10s while `SENDING`, otherwise 5 minutes); whatever records a receipt for a campaign (Twilio status webhook, `CampaignFeedbackService`) calls `CampaignReportService::forgetDeliveryStats`. Email delivered/opened/clicked events are written by the core delivery webhook, which knows no campaign, so those tiles can lag by the cache time.
- Addresses that outside services call (the one-click `List-Unsubscribe` header, Twilio webhooks) are built with `PublicApiUrl` (`app/Services/Infrastructure/Url`, shared with lifecycle emails), never from `APP_URL` directly: `APP_URL` when it names an address of its own (another host, port or path than the frontend), otherwise `<APP_FRONTEND_URL>/api`, which is where the all-in-one image, Cloud and the e2e stack serve the API while leaving `APP_URL` unset, empty or equal to the site. Tests assert the full expected address, and the e2e Twilio helper posts to the exact URL it signs.
- Campaign, automation and test emails go out through `MAIL_CAMPAIGNS_MAILER` when set (Cloud: `postmark-campaigns`, Postmark's `broadcast` stream, kept apart from the `lifecycle` stream that `postmark-broadcast` names on Cloud; the stream needs Custom unsubscribe handling and the delivery webhook), otherwise the default mailer, and from `MAIL_CAMPAIGNS_FROM_ADDRESS`/`NAME` when set (`CampaignMail::defaultFrom`; a branded sender name keeps the campaign address), otherwise `MAIL_FROM_ADDRESS`. `CampaignSenderName` resolves the name the same way. Support notifications (review requests, paused campaigns) go to `CampaignSupportInbox`, which treats an unset `APP_PLATFORM_SUPPORT_EMAIL` or the shipped `example.com` default as no inbox: the mail is skipped and the campaign waits in the admin review queue, and `CampaignSendGate` words its "contact us" messages without an address.
